# 字典树题型：让公共前缀共享路径

## 什么时候想到 Trie

字典树适合大量字符串围绕“前缀”进行重复操作：

- 查询某前缀是否存在；
- 统计多少字符串经过某前缀；
- 统计多少字符串恰好在某前缀结束；
- 保存经过前缀的附加信息，如下标、最大权值；
- 把后缀反转后转化为前缀问题。

它的核心不是“存字符串”，而是：**相同前缀只保存一次，并让所有相关字符串共享这段路径。**

## 节点里到底存什么

先根据查询目标选择字段：

- `pass/score`：多少字符串经过该节点；
- `end/cnt`：多少字符串恰好在该节点结束；
- `isEnd`：是否存在在此结束的字符串；
- `idxs`：经过该节点的字符串下标集合；
- `maxIndex`：若只需最大下标，可直接维护最大值以节省查询时间和空间。

“经过次数”和“结束次数”含义不同，是最常见的错误来源。

## 插入与查询模板

插入一个单词时，从根开始逐字符：

1. 把字符映射到子节点编号；
2. 不存在就创建节点；
3. 移动到子节点；
4. 更新该前缀需要保存的信息；
5. 单词结束后更新终点信息。

查询时走相同路径；任一子节点不存在即可失败。根节点代表空前缀，若题目允许空前缀，根上也要维护对应信息。

## Trie 与其他算法的组合

复杂字符串题往往不是单独使用 Trie：

- Trie + Z/KMP：Trie 判断历史单词是否等于当前前缀，Z/KMP 判断该前缀是否也是后缀；
- 正向 Trie + 反向 Trie：分别筛选前缀与后缀，再求候选交集；
- Trie + DFS：统计子树、枚举匹配或恢复答案；
- 字典序排序 + LCP：相同前缀在排序后连续，有时可以替代 Trie，代码更短且内存更小。

## Trie 与排序 LCP 如何选择

- 动态插入、在线查询、需要逐字符走状态：优先 Trie。
- 数据静态、只关心相邻或成组公共前缀：排序 + LCP 往往更简单。
- 字符集很小且节点多：数组子节点访问快，但空间较大。
- 字符集很大或稀疏：用哈希映射保存实际存在的子节点。

## 复杂度认识

Trie 的操作复杂度通常与字符串长度成正比，而不是与已存字符串数量成正比。设总字符数为 `L`，建树时间和节点数最坏均为 `O(L)`；但如果每个节点还保存下标列表，总附加存储也要把所有列表长度计算进去。

## 易错点检查表

1. 子节点是否正确初始化为空？
2. 字符到下标的映射是否越界？
3. 更新信息应发生在进入节点前还是后？
4. 要统计的是经过次数还是结束次数？
5. 当前字符串是否会错误地匹配自己，更新顺序是否应“先查询后插入”？
6. 后缀是否已通过反转统一成前缀方向？
7. 是否真的需要保存完整下标列表，还是一个计数/最大值就够？
